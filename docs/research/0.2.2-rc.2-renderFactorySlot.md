## 1. `RenderFactorySlot` 运行时语义

### 1.1 调用形态与 fallback 触发条件

`renderFactorySlot` 本身只是一个绑定到调用方的薄封装，返回一个 `<FactoryOutlet>` 元素，
不做任何定义查询（查询在组件渲染时发生）：

- `ren-rc2:src/client/scoped-slots.tsx:45-59` — `boundRenderFactorySlot(caller)`：闭包缓存
  （`scoped-slots.tsx:43` `factoryRenderCache` WeakMap），实现就是
  `(name, props, options) => <FactoryOutlet name inputProps slots={options?.slots} fallback={options?.fallback} caller/>`。
- `ren-rc2:src/client/scoped-slots.tsx:1017-1034` — `FactoryOutlet`：
  `:1032` `const definition = host.factoryOf(name)`；
  `:1034` `if (definition === undefined) return <>{fallback ?? null}</>`。

**fallback 的唯一触发条件就是 `host.factoryOf(name) === undefined`，即"该工厂名下没有任何
definition 登记"。** definition 存在时走 `FactoryOccurrence` →
`ren-rc2:src/client/scoped-slots.tsx:1009-1012`（`<Comp {...provided} {...inputProps}/>`），
工厂组件返回什么就渲染什么——组件 `return null` 时 outlet 就渲染空 Fragment，
`fallback` 不会被咨询。类型面的注释与此一致：
`slots-rc1:lib/types/index.d.ts:396`（"the **missing-definition** fallback"）。

rc.1 语义逐字相同：`ren-rc1:lib/client.js:1061-1069`
（`FactoryOutlet` 内 `if (definition === void 0) return <>{fallback ?? null}</>`）。

关键推论（直接决定第 4 条的方案 (a)）：宿主 rc.2 的 context-menu 包**已经注册了**
`contextMenu.button` 的 definition（见 3.1 / 4.3），所以在 rc.2 宿主上 fallback 分支永远不命中，
"`options.fallback` = 本包自绘 Menu"**兜不住"工厂组件返回 null"**这一失败模式；
它只能兜 rc.1 线（工厂 key 不存在）。

### 1.2 单例还是多登记项合并

工厂是**一名一定义**的单例，不存在列表槽那种多登记项合并渲染：

- rc.2：`slots-rc2:src/index.ts:1091-1093` — `registerFactory` 撞上已有 definition 直接
  `throw new Error('slot factory "x" already has a definition')`；definition 存于
  `factories: Map<string, FactoryRecord>`，`FactoryRecord.definition` 是单值
  （`slots-rc2:src/index.ts:1709-1716` `factoryRecord`）。
- rc.1：`slots-rc1:lib/index.js:77` 同一条 throw，语义一致。
- 读侧同样单值：`slots-rc2:src/index.ts:1151-1153` `factory(name)` 返回
  `record?.definition`（或 rc.1 `slots-rc1:lib/index.js:131-133`）。

"一个工厂 key 可被多处调用、每个调用是一个独立 keyed occurrence"
（`slots-rc2:src/index.ts:515` 注释 "one independently keyed occurrence"）说的是
**渲染次数**可以多，**登记项**始终只有一个 definition。故方案 (b)"把工厂 occurrence
并排渲染"在语义上只是"在行里再画一个宿主工厂按钮"，不产生任何合并效果。

### 1.3 调用未声明的工厂名

- **类型面**：`RenderFactorySlot` 的 `name` 形参约束为 `F extends keyof SlotFactoryMap & string`
  （`slots-rc2:src/index.ts:521-527`，rc.1 同构：`slots-rc1:lib/types/index.d.ts:399`），
  未在 `declare module '@deepseek-ai/dsh-client-ui-slots' { interface SlotFactoryMap … }`
  里合并过的名字**编译期报错**。本 fork 已在
  [src/client/contract/slots.ts:236-241](../../src/client/contract/slots.ts) 自行声明了
  `'contextMenu.button'`，所以类型面对我们不设限。
- **运行时**：不抛错。`host.factoryOf(name)` 对未知名字返回 `undefined`，outlet 走 1.1 的
  fallback 分支，最终渲染 `fallback ?? null`。工厂崩溃另有 `FactoryErrorBoundary`
  兜底并 `reportFactoryError`（`ren-rc2:src/client/scoped-slots.tsx:470-487`），
  渲染 `<div data-factory-error=…>` 占位，同样不冒泡。
- 唯一会主动 throw 的路径是**递归渲染同名工厂**与 **`options.slots` 选了工厂未声明的
  local 位**（`ren-rc2:src/client/scoped-slots.tsx:1035-1039`），本 fork 两者都不涉及。

## 2. rc.1 运行时，注入 `sidebar.workspaces` 槽位的组件 props 是否已含 `renderFactorySlot`

**已含，且类型上就是必填。** 两条证据链：

1. **类型面（rc.1 slots 包）**：槽位登记项组件的 props 合成类型
   `ComposedProps = PropsRuntime & PropsRenderSlots & `**`PropsRenderFactories`**` & PropsStore & InjectFace & MatchedShare & PropsLocale`
   （`slots-rc1:lib/types/index.d.ts:478`；`PropsRenderFactories` 定义为
   `{ renderFactorySlot: RenderFactorySlot }` 必填字段，
   `slots-rc1:lib/types/index.d.ts:406-408`）。`ctx.slots.register` 的 component 形参正是
   以 `ComposedProps` 为约束（`slots-rc1:lib/types/index.d.ts:795`）。
   也就是说 fork 的 `WorkspaceBrowserProps` 加上 `& PropsRenderFactories` 后，
   在 rc.1 类型面上是**必填**而不是可选。
2. **运行时（rc.1 renderer）**：渲染任何登记项时，标准 kit 无条件携带
   `renderFactorySlot: boundRenderFactorySlot(entry)`
   （`ren-rc1:lib/client.js:736-741`，kit 展开进组件：`ren-rc1:lib/client.js:772-793`
   `<Comp {...kit} {...injected} … {...ownerProps}/>`）。宿主 sidebar 侧的
   `renderSlot("sidebar.workspaces", { wide, expandSidebar })`
   （`sb-rc1:lib/client.js:543-549`）只是 owner props；`renderFactorySlot` 从来不归
   sidebar 穿，归 renderer 注。rc.2 同构：`ren-rc2:src/client/scoped-slots.tsx:603`。

一个易混点：宿主 rc.1 **自家**的 `WorkspaceBrowserProps` 契约没有合成这一项
（`ws-rc1:lib/types/client/contract/slots.d.ts:495` 的交集里没有 `PropsRenderFactories`），
rc.2 才补上（`ws-rc2:src/client/contract/slots.ts:495-497`）。但这只是宿主没**声明**、
宿主 rc.1 的行组件没**消费**——注入照旧发生。反证是宿主 rc.1 自己的 Toast 行就在用：
`ws-rc1:lib/client.js:4557-4558` `const { …, renderFactorySlot, … } = props;
return renderFactorySlot("workspace.toast.content", …)`——rc.1 运行时该 prop 实到且可调用。

**对本 fork 的含义**：加 `& PropsRenderFactories`（必填）在 rc.1 / rc.2 两代上都成立，
不存在"rc.1 上可能 undefined 需要判空"的问题；透传链（task-2）可以放心按必填穿。

## 3. rc.1 时代有没有 `contextMenu.button` 工厂注册

**没有。** `grep -c registerFactory cm-rc1/package/lib/client.js cm-rc1/package/lib/index.js`
两代产物均为 **0**（rc.1 的 context-menu 包根本没有工厂用法；它只
`ctx.slots.inject("shell.overlay", …)` 登记普通槽 `contextMenu.content` / `contextMenu.icon`，
`cm-rc1:lib/client.js:1405-1417`）。rc.2 才引入：

- 类型声明：`cm-rc2:src/client/index.ts:34-37` —
  `interface SlotFactoryMap { 'contextMenu.button': { scope:'root'; props: ContextMenuButtonProps; inject: ContextMenuButtonInjected } }`
- 运行时注册：`cm-rc2:src/client/index.ts:135-147` — `ctx.slots.registerFactory({ name:'contextMenu.button', … }, ContextMenuButton)`。

含义链（结合 1.1 / 2）：

- rc.1 运行时工厂 map 里**不存在** `contextMenu.button` 这个 key → 任何调用（包括 fork 若
  在 rc.1 上消费）只会得到 `fallback ?? null`，不会报错；
- rc.1 的行按钮本来就是宿主自绘：`ws-rc1:lib/client.js:2655-2660`
  （`openSessionMenu(…)` + `IconEllipsisOutlineRegular`），与工厂无关；
- 因此"对齐 rc.2 的工厂消费"这件事**只可能在 rc.2 宿主上产生可观察差异**，
  rc.1 宿主上任何 (a)/(b) 变体都退化为 fallback/空渲染——这正是 (a) 里
  `fallback=本包 Menu` 看起来安全的原因，但它管不住 rc.2 的 null 分支（见 4.3）。

## 4. 决策：fork 应采用 (a)/(b)/(c) 哪种

### 4.1 三个方案的机制复盘

- **(a) 触发区整体换 `renderFactorySlot('contextMenu.button', { …, fallback: 本包 Menu })`**
  - rc.1：definition 缺失 → 渲染 fallback（本包 Menu）→ 与现状一致 ✔（1.1、3）。
  - rc.2：definition 存在 → **fallback 死代码**；且本包安装形态下 kind 贡献已缺失
    （见下两条与 4.2），最先撞到的失败模式就是按钮整个消失。即便补齐 kind，
    行菜单也整体换为宿主共享工厂按钮 →
    点击打开的是宿主 `contextMenus` 服务的共享弹层（`cm-rc2:src/client/index.ts:138-145`
    `toggle → contextMenus.open`），菜单内容 = 宿主 contextMenus 贡献集合，
    **本包私有槽 `sidebar.workspaces.session.menu.item` 的条目（pin/rename/fork/archive/
    session-id，[src/client/index.ts:451-456](../../src/client/index.ts)）从行上消失**，
    外部插件按 README 承诺注册进该扩展面（docs/upgrading.md:125）的条目也一并消失。这是真回归。
  - 更糟：本包安装形态把宿主 ui-workspace 整包 disable（`cordis.patch.yml`，见 4.2），
    `registeredKinds` 里 `session`/`workspace` 两个 kind 根本不存在 → rc.2 标准安装下
    工厂组件直接 `return null`、fallback 又不救（1.1）→ **行菜单触发器整体消失**，
    连"内容易主"都到不了。
- **(b) 保留本包 kebab + 工厂 occurrence 并排**
  - rc.2 上宿主 `ContextMenuButton` 渲染的同样是一个"…"省略号按钮
    （`cm-rc2:src/client/Button.tsx:37-50`），与本包 kebab（本仓 Rows.tsx:303-318、709-731）
    并排 = **两个几乎相同的省略号按钮**，一个开本包菜单、一个开宿主共享菜单；
    且工厂是单例（1.2），并排渲染不带来任何"合并登记项"收益。
- **(c) 只透传 `renderFactorySlot`、不主动消费；台账/README 明示差异**
  - 两代行为与现状逐像素一致（本包 kebab Menu 不变）；类型面对齐 rc.2
    的 `WorkspaceBrowserProps`（第 2 条已证 rc.1 也满足必填）；
    Issue #50 建议 1 明确允许此路径。

### 4.2 关键风险核验："rc.2 下 ContextMenuButton 因 kind 未注册返回 null"是否真实

**真实，且在标准安装形态下必然发生。** 证据链三段：

1. null 门本身：`cm-rc2:src/client/Button.tsx:33-34` —
   `const available = useRegisteredKinds(kinds => kinds.includes(target.kind)); if (!available) return null`。
   `registeredKinds` 来源链：`cm-rc2:src/client/registry.ts:17-19`
   （`MenuRegistry.kindsSource`，每次 `register`/`unregister` 贡献时 `publishKinds()`，
   `cm-rc2:src/client/registry.ts:40-44`）→ `cm-rc2:src/client/index.ts:99,138` 暴露给工厂 inject。
2. kind 贡献的唯一来源是**宿主 ui-workspace 包自身**（不是 context-menu 包）：
   `workspace` kind = `ws-rc2:src/client/index.ts:323-328` 两条
   `ctx.contextMenus.register({ id:'workspace.rename'|'workspace.delete', target:'workspace' })`；
   `session` kind = `ws-rc2:src/client/index.ts:386` `registerSessionMenus(ctx, …)` →
   `ws-rc2:src/client/session-actions/context-menus.tsx:26-27`
   （`id:`session.${id}`, target:'session'`）。本 fork 的 `src/` 无任何
   `contextMenus.register` 调用，两个 kind 都不靠我们自己。
3. **本包的安装形态把宿主 ui-workspace 整个 disable 了**：
   [cordis.patch.yml](../../cordis.patch.yml) 全文即"insert `dsh-group-status` +
   `- id: ui-workspace / disabled: true`"；[README.md:63](../../README.md)
   （"它注册同一个槽位，并在 profile 里禁用官方 `ui-workspace` 行"）与
   [docs/upgrading.md:3](../../docs/upgrading.md)
   （"同一个侧栏槽位再注册一份，并把官方那一行 disable"）同此。
   包被禁用 ⇒ 其 apply effects 根本不跑 ⇒
   `session`/`workspace` 两个 kind 贡献**不存在**于 `registeredKinds`。

三条叠加（再叠加 1.1 的"fallback 只在 definition 缺失时触发"——rc.2 上 context-menu 包的
definition 是在的，fallback 永不命中）：**若 fork 直接消费工厂按钮，rc.2 上
`ContextMenuButton` 对 `{kind:'workspace'}` / `{kind:'session'}` 一律 `return null`，
分组行与会话行的"…"触发器整体消失，且 options.fallback 救不回来——(a) 是确定性回归，
不是概率性风险。**
rc.1 的宿主 workspace 虽同样注册这些贡献（`ws-rc1:lib/client.js:4331-4333`、`5955-5970`），
但 rc.1 根本没有这个工厂（第 3 条），所以差异只在 rc.2 一代显形。

> 修正记录（2026-11-12，lead 指出）：本节初稿曾误判"fork 只是影子化
> `sidebar.workspaces` 单槽、宿主 ui-workspace 包仍装载、kind 贡献照跑、null 风险不真实"。
> 该前提被 `cordis.patch.yml` 证伪——profile 补丁禁的是整个官方包，effects 不执行。
> 结论由"标准配置下非真实风险"更正为"**标准安装形态下必然触发**"。

### 4.2b 顺带核查：`sidebar.panel.icon` 工厂与 fork 的关系

**核过：`sidebar.panel.icon` 与 fork 无关，issue 的"面板图标在分组行缺失"表述只成立于
`contextMenu.button` 一处。** 依据：rc.2 宿主对 `sidebar.panel.icon` 的唯一消费点在
**面板列表条目**（`sb-rc2:src/client/SidebarRoot.tsx:92`，包被我们禁用），不在工作区
分组行；宿主 rc.2 的分组行左侧本来就画文件夹图标
（`ws-rc2:src/client/rows/Rows.tsx:315` `IconFolderOpenRegular`/`IconFolderCloseRegular`），
fork 同构自绘（本仓 Rows.tsx:292），两边一致。宿主 ui-workspace rc.2 全包内
`sidebar.panel.icon` 零引用。所以 fork 未消费的工厂只有 `contextMenu.button` 一个。

### 4.3 推荐

**采用 (c)**：task-2 的透传链保持并作为本次 PR 的全部消费面（行组件收下
`renderFactorySlot` 但不调用，[src/client/rows/Rows.tsx:262,596](../../src/client/rows/Rows.tsx)
的 JSDoc 已按"threaded only"落注）；在 docs/upgrading.md 与 README 兼容性表明示。**"差异"的准确表述**（写台账就用这句）：
本包行组件对齐 rc.2 的 `PropsRenderFactories` 透传面，但**有意不消费**
`contextMenu.button` 工厂——本包的菜单体系是自带的（行内自绘 Menu + 自有
`sidebar.workspaces.session.menu.item` 列表槽），从不接入宿主共享
contextMenus 体系；因此在宿主 rc.2 上，**其它插件经共享 context menu 体系登记的贡献**
（`contextMenus.register` 动作、`contextMenu.content` 自定义内容、
`contextMenu.button` 工厂 occurrence）**不会出现在本包 fork 的行与菜单里**；
而经 `sidebar.workspaces.session.menu.item` 槽注册的菜单项在本包本地菜单**照常出现**
（本包渲的就是这同一个槽）。差异只在 rc.2 一代显形（rc.1 没有该工厂，见第 3 节）。

理由（对应 Issue #50 三选一）：

1. (a) 在本包的安装形态下是**确定性回归**（4.2：ui-workspace 被 disable → kind 贡献缺失 →
   工厂组件对两种 target 一律 `return null`，且 fallback 在 definition 存在时永不触发），
   行菜单触发器直接消失；
2. (b) 语义上不产生合并（1.2 单例）；且在 (a) 的 null 链下并排的工厂 occurrence 同样渲染
   为空，等于白加一条调用边——若为让它出按钮而自行补 `contextMenus.register` 贡献，
   实际已滑向"完整共享菜单迁移"，与 (b) 的名义最小改动不符；
3. (c) 零行为变化、零回归，类型面与 rc.2 完全对齐，且是 issue 建议 1 明文允许的路径；
   台账把"未消费工厂"记为**有意差异**而非遗漏。
4. 若将来要做真正的共享菜单对齐，应单独立项：把 pin/rename/fork/archive/session-id 迁成
   `ctx.contextMenus.register` 贡献（补上被 disable 的官方包留下的 kind 空洞）、
   行上挂 `useContextMenu().getTriggerProps`，再切工厂按钮——那时 null 门与内容源才同时成立。
